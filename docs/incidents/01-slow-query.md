# Slow Query

## Symptoms

A support dashboard request exceeds its normal response window and active sessions show the statement running longer than neighboring queries.

## Investigation

Identify the exact statement and parameters, inspect `pg_stat_activity`, then capture a plan with `EXPLAIN (ANALYZE, BUFFERS)` in a safe lab or staging context. Compare estimated rows, actual rows, scan types, sorts, joins, and buffer activity.

## SQL commands used

```sql
SELECT pid, query_start, CURRENT_TIMESTAMP - query_start AS age, wait_event_type, wait_event, query
FROM pg_stat_activity
WHERE state <> 'idle'
ORDER BY query_start;

EXPLAIN (ANALYZE, BUFFERS, VERBOSE)
SELECT id, priority_id, updated_at
FROM tickets
WHERE organization_id = 10
  AND status IN ('open', 'pending')
ORDER BY updated_at DESC
LIMIT 50;
```

## Evidence

The captured plan and session age are the evidence. Do not infer the cause from elapsed time alone; determine whether time is spent scanning, sorting, joining, waiting on a lock, or reading pages.

## Root cause

For this lab scenario, the query shape is intentionally tested against an unindexed temporary copy in `performance/01_missing_index_demo.sql`, making the access path the controlled root cause.

## Resolution

Add an index that matches the selective predicates and requested ordering, then run `ANALYZE` and recapture the plan.

## Verification

Compare the before/after artifact files generated by `make performance`. Confirm the result set is unchanged and review scan type, sort behavior, actual rows, and buffers.

## Prevention

Review slow-query evidence before adding indexes, keep statistics current, validate high-value query paths in CI/staging, and avoid treating every slow query as an indexing problem.
